# MandiMitra AI — API Design (v1)

Base URL: `/api/v1` · JSON · Auth: HttpOnly cookies (`mm_at`, `mm_rt`) · OpenAPI 3.1 is generated from the Zod schemas (`/api/v1/docs` in non-production builds).

## 1. Conventions

### Response envelope
```jsonc
// success
{ "success": true, "data": { ... }, "meta": { "page": 1, "pageSize": 25, "total": 312 } }

// error
{ "success": false, "error": { "code": "LOT_QTY_EXCEEDED", "message": "बिक्री वजन लॉट में उपलब्ध वजन से अधिक है", "details": { "availableKg": "1250.000" } }, "requestId": "01J…" }
```
- `message` follows `Accept-Language` (`hi` or `en`). With no header it **defaults to Hindi** (Hindi-first product). `code` is stable and the frontend uses it. The catalogue lives in [`packages/shared/src/errors.ts`](../packages/shared/src/errors.ts).

> **Implemented as of Phase 3:**
> - `/auth/*` (register, login, refresh, logout, me, switch-business, change-password, invite preview/accept)
> - `/businesses/current[/settings]` and `/staff` (list, roles, invites, membership update, activity, audit-log)
> - `/farmers` (list/search/filter/sort, villages, CRUD, summary, bank accounts with masked list, logged reveal and delete)
> - `/buyers` (list incl. `hasOutstanding`, CRUD, summary)
> - `/commodities` (list, create, update, grades)
> - `/reports/dashboard`
> - `/healthz` and `/readyz`
>
> - **Phase 4:** `/lots` (list/filter incl. `status=OPEN`, create (draft or confirmed), PATCH draft with `version`, confirm, cancel); `/sales` (list with totals, create, cancel); `/purchases` (list incl. `unbilled`, manual create in TRADER/MIXED mode, cancel); `/patti` (list, `POST /preview`, finalize, get, `/print` HTML, `/pdf`, cancel); `/commission-rules` (list, create, update); `/calculate/{amount,sale,lot}`; `/approvals` (list, approve, reject)
>
> - **Phase 5:**
>   - `/payments`: list with paid-out and received totals, create (Idempotency-Key, stored on the row as a second DB-level guard), get, `/receipt` (HTML or `?format=pdf`), cancel.
>   - `/ledger/{farmers|buyers}/:id`: `?from&to&format=json|html|pdf`.
>   - `/expenses`: list with totals by category, create, cancel, plus `/categories` CRUD.
>   - `/reports/:key`: `daily-arrivals, purchases, sales, farmer-outstanding, buyer-outstanding, commission, expenses, stock, monthly-summary, commodity-wise`, with `?from&to&format=json|html|pdf|xlsx&lang=hi|en`.
> - **Phase 6:**
>   - `/ai`: `usage`, `conversations[/:id]`, `POST ask`, `POST extract` (text or base64 photo ≤ 5 MB → draft), `drafts/:id` `GET`, `confirm`, `discard`, and `POST reminder`.
>   - `/notifications`: list with `meta.unread`, `/:id/read`, `/read-all`, `POST /whatsapp/send` (`kind: PATTI|STATEMENT|RECEIPT|REMINDER`, Idempotency-Key), and `GET /whatsapp/messages`.
>   - `GET|POST /webhooks/whatsapp`: Meta verify handshake and signed callbacks.
>
> Everything else below is the agreed design for later phases.
>
> **Phase 6 notes (as built):**
> - **AI endpoint errors:**
>   - `503 AI_NOT_CONFIGURED` when no key is set.
>   - `402 PLAN_LIMIT_REACHED {resource:"ai"}` when the plan lacks AI or the monthly quota is used.
>   - `422 AI_COULD_NOT_READ` for unreadable input.
>   - `422 AI_CONVERSATION_FULL` after 40 questions.
> - **Permissions:** `ai:query` (all roles), `ai:draft` (owner and munim), `whatsapp:send` (owner and munim, also for reminders).
> - **WhatsApp send errors**, checked in this order:
>   - `402` if the plan has no WhatsApp;
>   - `422 WHATSAPP_CONSENT_REQUIRED`, then `NO_MOBILE`, then `PDF_UNAVAILABLE`;
>   - `502 WHATSAPP_SEND_FAILED` (the attempt is still recorded as FAILED, with the provider's error code).
>
> **Phase 5 notes (as built):**
> - **Farmer payments:**
>   - `SETTLEMENT` can never exceed the payable balance, checked under a row lock (`422 PAYMENT_EXCEEDS_PAYABLE`), so concurrent settlements cannot overdraw.
>   - `ADVANCE` may take the balance negative unless `allowNegativeFarmerBalance` is off.
> - **Buyer `COLLECTION`:** overpayment is allowed and returned as `meta.warnings[OVERPAYMENT]`. The excess becomes a buyer credit.
> - **Repeated references:** a repeated UTR or cheque number for the same mode returns `meta.warnings[DUPLICATE_REFERENCE]`. It's a warning, not a block, because cheque numbers repeat across banks.
> - **Statements** order by business date and then insertion sequence, so back-dated entries land where they belong. The running balance is recomputed server-side with Decimal.
> - **Exports:** PDF/XLSX need `report:export` (owner and munim; not viewer) and an export-enabled plan, and are logged as `REPORT_EXPORTED`. JSON and HTML views need only `report:read`.
> - **XLSX** is generated by an in-house writer ([`backend/src/utils/xlsx.ts`](../backend/src/utils/xlsx.ts)) using Node zlib only. `exceljs` was evaluated and rejected: 168 transitive packages and an open advisory.
> - **Buyer ageing** applies payments to the oldest debits first (FIFO). Reversed sales are excluded.
>
> **Phase 4 notes (as built):**
> - **No draft pattis.** `POST /patti/preview` is a read-only computation and `POST /patti` creates a FINALIZED patti in one transaction. Fewer states and nothing half-finished on the ledger. To change a patti, cancel it (reversal) and create a new one.
> - **Idempotency-Key is required** on `POST /lots`, `/sales`, `/purchases`, `/patti` and every `/:id/cancel`:
>   - a repeat of the same key replays the stored response (header `Idempotent-Replayed: true`);
>   - the same key with a different body returns `422 IDEMPOTENCY_KEY_REUSED`;
>   - a concurrent duplicate returns `409 REQUEST_IN_PROGRESS`;
>   - a non-2xx outcome releases the key.
> - **Cancel endpoints** return `200 {status:"CANCELLED", record}`, or `202 {status:"PENDING_APPROVAL", approvalRequest}` when a munim's cancellation needs the owner (`requireApprovalForCancel`). Approving runs the cancellation in the same transaction as the decision.
> - **Trading modes:**
>   - `COMMISSION_AGENT`: a sale auto-creates the farmer purchase at the same weight and rate, and manual purchases return `422`.
>   - `TRADER`: sales require purchased stock (`STOCK_NOT_PURCHASED`).
>   - `MIXED`: the sale body takes `mode: COMMISSION|TRADE`.
> - **Patti documents** render from the frozen `farmerSnapshot` and `businessSnapshot`, so later renames don't change printed history. `/print` is self-contained HTML under a strict CSP. `?print=1` opens the print dialog and `/pdf?download=1` downloads.
>
> **Phase 3 notes:**
> - Bank account reveal is `POST /farmers/:id/bank-accounts/:accountId/reveal`. It's a POST because it has a side effect (an access-log entry), and responses are `Cache-Control: no-store`.
> - Create responses for farmers and buyers may carry `meta.warnings`, e.g. `DUPLICATE_MOBILE` or `DUPLICATE_GSTIN`. These are non-blocking.
> - Opening balance is accepted on create only. It posts an `OPENING_BALANCE` ledger entry inside the same transaction.
> - Farmers and buyers with a non-zero balance cannot be archived (`422 FARMER_HAS_BALANCE` / `BUYER_HAS_BALANCE`).
- Money and weight are sent as **strings**: `"amount": "125000.00"`, `"weightKg": "4050.500"`.
- Dates are `YYYY-MM-DD` for business dates and ISO-8601 UTC for timestamps.

### Status codes
`200` OK · `201` created · `204` no content · `400` validation (`VALIDATION_ERROR`, with zod issues in details) · `401` unauthenticated · `402` subscription inactive / plan limit · `403` missing permission · `404` not found **or other tenant** · `409` conflict (version mismatch, invalid state transition) · `422` business-rule violation · `429` rate limited · `500`.

### Lists
`GET /farmers?page=1&pageSize=25&q=ram&sort=-createdAt&village=Kharkhoda&isActive=true`
- `pageSize` ≤ 100. Offset pagination for admin-sized lists. Ledgers and audit logs use **cursor** pagination (`?cursor=<seq>`).
- Date-filterable resources accept `from`, `to` (inclusive) or `range=today|yesterday|week|month`.

### Headers
| Header | Use |
|---|---|
| `X-Requested-With: mandimitra` | Required on POST/PUT/PATCH/DELETE (CSRF guard) |
| `Idempotency-Key: <uuid>` | Required on financial POSTs: sales, purchases, pattis/finalize, payments, expenses, cancellations |
| `If-Match: <version>` | Optimistic concurrency on lot and patti updates |
| `X-Request-Id` | Echoed or generated; appears in logs |

### Billing — `/billing` (SaaS subscription, Phase 7)
No read-only gate here: an expired or past-due business can always see its plan and pay. 🔑 = `subscription:manage` (owner); reads need `subscription:read` (owner, munim).
| GET | `/billing/plans` | Active plans (server prices). `meta.provider`: `razorpay` or `mock` |
|---|---|---|
| GET | `/billing/subscription` | Effective status, plan, trial/period dates, pending downgrade, usage vs limits |
| POST 🔑 | `/billing/checkout` | `{planCode}` only. Creates a Razorpay order for the plan's server-side price → `{orderId, keyId, amountPaise, kind: NEW|RENEWAL|UPGRADE}`. A smaller plan while a paid period is live → `409 PLAN_CHANGE_AT_RENEWAL` |
| POST 🔑 | `/billing/verify` | `{orderId, paymentId, signature}` from Checkout. HMAC verified with the key secret; bad signature → `400 PAYMENT_VERIFICATION_FAILED`, nothing changes. Idempotent |
| POST 🔑 | `/billing/change-plan` | `{planCode}` smaller plan from the renewal date. Too many active staff → `422 DOWNGRADE_BLOCKED_STAFF`; farmer over-limit returns `warnings` |
| POST 🔑 | `/billing/change-plan/cancel` | Undo a scheduled downgrade |
| POST 🔑 | `/billing/cancel` · `/billing/resume` | Stop (or keep) at period end. Needs a live paid period |
| GET | `/billing/payments` | History (paid, failed, incomplete) |
| GET | `/billing/payments/:id/receipt` | Printable HTML payment receipt (not a tax invoice) |
| POST 🔑 | `/billing/mock/complete` | **Dev only** (`BILLING_PROVIDER=mock`, never in production): plays the Checkout popup for an order of this business, returning a validly signed `{paymentId, signature}` |
| POST | `/webhooks/razorpay` | No session. `X-Razorpay-Signature` = HMAC-SHA256(raw body, webhook secret). De-duplicated by `X-Razorpay-Event-Id`. `payment.captured` / `order.paid` activate (amount must equal the order), `payment.failed` records the reason |

**Period rules:** prepaid 30-day periods, one order each, nothing charged automatically. Paying during a live trial starts the period when the trial ends; renewing early appends to the current period; upgrading starts now and adds the unused value of the old plan as extra days (`remaining × oldPrice ÷ newPrice`).

### Health
`GET /healthz` · `GET /readyz`
